# MNEME v0.1 — Canonical Memory Layer and MLF-RM Residence Memory Profile

**Status:** Architecture baseline / design specification  
**Date:** 2026-08-27  
**Repository:** `kakon77777-commits/MNEME`  
**Initial profile:** `MLF-RM/0.1`

## 1. Purpose

MNEME defines a canonical memory layer for Residence-aware AI systems.

The central design decision is simple:

```text
MEMORY.md != MEMORY
```

Markdown remains useful as a human-readable and model-readable projection, but it is not required to be the canonical memory state. Canonical memory is represented as typed, bounded, independently validatable records connected by explicit routes, relations, provenance, and transaction receipts.

The design is motivated by a concrete failure class observed in current AI memory workflows: a large Markdown memory file may be loaded only partially by a host, while the underlying file remains complete. From the agent's point of view, an omitted rule may become indistinguishable from a rule that never existed. Similarly, an LLM rewriting a long document may stop before the intended write is complete. A format that is syntactically valid after truncation can therefore conceal semantic data loss.

MNEME changes the failure mode. A partial model output must not become a partial canonical write. Context materialization must be budget-bounded independently of total memory size.

## 2. Relationship to existing systems

MNEME is a new layer, not a replacement for the surrounding systems.

```text
SEDB-RAL
  Canonical resident / instance / continuity / address / authority evidence
        |
        v
LIMEN
  Host observation / identity resolution / minimum authorization
        |
        v
AI Residence
  Private custody boundary for identity, memory, relationships, projects,
  checkpoints, and audit state
        |
        v
MNEME
  Canonical memory records / relations / routes / provenance / transactions
        |
        v
SOACR
  MemoryNeed / provider selection / routing / reconstruction / continuation
        |
        v
Working Context
```

Responsibilities remain separated:

- **SEDB-RAL** owns residency and attestation evidence.
- **LIMEN** owns host-to-resident identity mediation and minimum access authorization.
- **AI Residence** owns private custody boundaries.
- **MNEME** owns canonical memory representation and memory-state transaction semantics.
- **SOACR** owns memory need, retrieval strategy, reconstruction, and continuation behavior.
- **MLF** remains the general structural-first matrix-ledger format lineage.
- **MMLC** remains a computation/runtime lineage; MNEME may later use compatible route/audit ideas without redefining MMLC.

No component is allowed to infer identity from memory style, display name, model identity, project name, or remembered prose.

## 3. Design principles

### 3.1 Canonical memory is not working context

Let canonical memory at time $t$ be $M_t$, and the context materialized for a specific model turn be $C_t$.

$$
C_t = P(M_t, I_t, T_t, N_t, B_t)
$$

where:

- $I_t$ is the resolved and authorized identity state;
- $T_t$ is the current task state;
- $N_t$ is the declared or derived memory need;
- $B_t$ is the context budget;
- $P$ is a deterministic or auditable projection/materialization function.

The required runtime invariant is:

$$
|C_t| \le B_t
$$

MNEME does **not** require:

$$
|M_t| \le B_t
$$

Total persistent memory capacity must therefore not be coupled to the size of a single prompt, Markdown bootstrap file, provider response, or model output.

### 3.2 Markdown is a projection

A Markdown view is derived from canonical memory:

$$
D_t = P_{\mathrm{md}}(M_t, Q_t)
$$

where $Q_t$ contains projection policy such as scope, identity, route, priority, and byte/token budget.

A `MEMORY.md` projection may be regenerated at different sizes without deleting or mutating canonical records.

### 3.3 Writes are transactions, not document rewrites

The model should propose bounded records or bounded transactions. It should not be required to rewrite an unbounded canonical document.

A write transaction $T$ is committed only if all mandatory parts are present and valid:

$$
\operatorname{Commit}(T)=
\begin{cases}
1, & \text{if parse, schema, authority, digest, count, and final marker pass}\\
0, & \text{otherwise}
\end{cases}
$$

A truncated output therefore fails closed.

### 3.4 Storage backend is replaceable

MNEME v0.1 is file-first. Future dynamic-database work may implement the same canonical contracts, but database choice must not redefine record semantics, routing semantics, commit semantics, or projection semantics.

```text
STORAGE BACKEND != MEMORY SEMANTICS
```

## 4. Core invariants

MNEME v0.1 adopts the following invariants:

```text
IDENTITY != MEMORY
MEMORY != CONTEXT
MEMORY != MARKDOWN
CANONICAL STATE != PROJECTION
READ AUTHORITY != WRITE AUTHORITY
PROPOSAL != COMMIT
PARTIAL OUTPUT != VALID TRANSACTION
MODEL CONTEXT BUDGET != MEMORY CAPACITY
ROUTE != RECORD
INDEX != CANONICAL CONTENT
STORAGE BACKEND != MEMORY SEMANTICS
RENDERING SUCCESS != CANONICAL COMMIT
```

These are testable runtime boundaries, not documentation slogans.

## 5. MLF-RM profile

The initial canonical profile is named:

```text

Matrix Ledger Format — Residence Memory Profile
```

MLF-RM inherits the structural-first principle from MLF: preserve typed structure first, and derive sequence/human/model/graph views as projections.

## 6. Canonical record model

Every canonical memory item is a `MemoryRecord`.

A minimum record contains:

```json
{
  "record_version": "mneme.memory-record/0.1",
  "record_id": "uuid-or-content-addressed-id",
  "record_type": "lesson",
  "scope": {
    "kind": "global",
    "subject": "verification"
  },
  "content": {
    "text": "A verifier must itself be validated."
  },
  "relations": [],
  "provenance": {
    "event_id": "...",
    "source_ref": "..."
  },
  "status": "active"
}
```

The exact JSON schema is an implementation artifact for the next phase; this design fixes only the semantic fields that must exist.

### 6.1 Record types

The initial vocabulary is deliberately small:

- `identity`
- `instruction`
- `fact`
- `lesson`
- `episode`
- `project`
- `relation`
- `current`

New record types require profile-version evolution or declared extensions. Arbitrary new fields must not silently become canonical semantics.

### 6.2 Scope

Scope is explicit and machine-readable. At minimum:

- `global`
- `identity/<resident-or-local-id>`
- `project/<project-id>`
- `task/<task-id>`
- `method/<method-id>`

A record may be reachable through multiple routes without being duplicated into multiple canonical copies.

## 7. Route model

A route is a retrieval/materialization declaration, not the record itself.

Examples:

```text
route://global/tier0
route://identity/<id>/bootstrap
route://identity/<id>/current
route://project/<project-id>
route://method/verification
```

Routes may select records by explicit IDs, typed predicates, graph relations, or bounded rules. Route resolution must be auditable: the runtime must be able to explain why a record was selected or omitted.

This replaces the need for an ever-growing human-maintained top-level Markdown hyperlink index.

## 8. Transaction model

### 8.1 Proposal first

Model output is never canonical merely because it was generated. The model creates a proposal.

```text
LLM / agent
  -> proposed record(s)
  -> parser
  -> schema validation
  -> scope validation
  -> identity / authority validation
  -> provenance validation
  -> digest calculation
  -> staging
  -> final commit validation
  -> canonical append
```

### 8.2 Transaction envelope

A transaction contains:

- transaction version;
- transaction ID;
- expected source head;
- declared record count;
- ordered record digests;
- authority reference;
- optional projection requests;
- final transaction digest;
- explicit commit marker.

The commit marker must be outside individual record content so a truncated final record cannot accidentally look committed.

### 8.3 Truncation behavior

The expected failure behavior is:

```text
complete proposal + complete commit marker -> eligible for validation
complete records + missing commit marker    -> no commit
partial final record                        -> parse fail -> no commit
wrong declared count                        -> no commit
wrong digest                                -> no commit
wrong expected head                         -> no commit
unknown authority                           -> no commit
```

No recovery path may reinterpret a partial transaction as a successful canonical write.

### 8.4 Idempotence

A fully committed transaction retried against the same canonical head must either:

1. return the existing receipt as an idempotent replay; or
2. reject because the expected head no longer matches.

It must not duplicate records silently.

## 9. Projection model

MNEME supports multiple projections from the same canonical memory state.

Initial projection classes:

- **human Markdown** — readable summaries, `MEMORY.md`, identity/current views;
- **model context** — bounded prompt/context materialization;
- **structured view** — JSON/JSONL subset for tools and providers;
- **graph view** — explicit relation/dependency/continuity view;
- **audit view** — provenance and transaction receipts.

A projection manifest records:

- source canonical head;
- route or query;
- materialization policy;
- byte/token budget when relevant;
- included record IDs;
- omitted record count/reasons when applicable;
- projection digest.

A valid projection proves what was materialized; it does not grant authority to mutate the source memory.

## 10. Budgeted context materialization

Context overflow is handled before model invocation.

Given a budget $B$ and candidate records $R=\{r_1,\ldots,r_n\}$, the materializer selects an auditable subset or compressed projection $S$ such that:

$$
S \subseteq R
$$

and

$$
|P_{\mathrm{model}}(S)| \le B
$$

Selection policy belongs to the materialization/routing layer. Canonical memory is not deleted because a model cannot consume it in one turn.

If mandatory bootstrap content cannot fit the declared budget, the operation must fail explicitly or select a higher-level bounded bootstrap projection. Silent tail truncation is forbidden as a successful MNEME materialization result.

## 11. Tier mapping

Existing Tier 0 / Tier 1 memory designs map naturally into routes.

### Tier 0

Always-eligible bootstrap material:

- cross-project communication rules;
- cross-project hard constraints;
- minimal identity registry pointers;
- canonical location/service pointers.

Tier 0 should be a bounded projection, not an ever-growing store.

### Tier 1

Identity-specific bootstrap material:

- identity role and local operating context;
- current continuation state;
- identity-local memory routes;
- identity-specific relations.

### Deeper recall

Project, method, episode, research, and long-history records remain canonical but are materialized only when a `MemoryNeed` or route requires them.

## 12. Markdown import and migration

MNEME v0.1 must support non-destructive migration from existing Markdown memory without assuming Markdown structure is semantically complete.

The migration pipeline is:

```text
source Markdown
  -> parse blocks / headings / lists / links / source lines
  -> propose typed records and routes
  -> produce import-loss report
  -> validate
  -> commit into a new MNEME store
  -> project a comparison Markdown view
```

The source Markdown is never overwritten by import.

Any uncertain mapping must be recorded as uncertain or unmapped. The importer must not fabricate identity, authority, relation, or temporal meaning solely from prose layout.

## 13. Integration boundaries

### 13.1 SEDB-RAL

MNEME may store references to resident, instance, continuity, address, and authority evidence, but does not mint or merge those identities.

```text
SEDB-RAL evidence -> identity reference
identity reference != MNEME-generated identity
```

### 13.2 LIMEN

Private memory access requires a resolved identity and authorization envelope or an equivalent future contract. MNEME does not bypass LIMEN by searching private memory first and then guessing the resident.

### 13.3 AI Residence

AI Residence is the custody boundary. MNEME defines the memory format/runtime semantics inside an authorized Residence scope; it does not make the entire Residence public or globally searchable.

### 13.4 SOACR

SOACR consumes MNEME through provider/route interfaces. A canonical relationship is:

```text
MemoryNeed
  -> authorized route/query
  -> MNEME records/projection
  -> SOACR validation/reconstruction
  -> Working Context
```

SOACR proposal-only writeback may later target MNEME transactions, but no direct unvalidated document rewrite is allowed.

## 14. Fingerprints and integrity

MLF-RM should eventually expose at least three independently useful digests:

1. **structural fingerprint** — record topology, scopes, routes, relations;
2. **content fingerprint** — canonical record content;
3. **projection fingerprint** — a specific materialized view.

A future semantic fingerprint may be added only when its normalization semantics are precise enough to test deterministically.

`checksums.json` binds file-level package integrity. Canonical transaction receipts bind logical state evolution.

## 15. Failure model

MNEME treats the following as explicit failures rather than acceptable degraded success:

- truncated transaction;
- missing commit marker;
- malformed JSON/JSONL record;
- duplicate canonical ID with conflicting content;
- unknown or invalid schema version;
- route resolving outside authorized scope;
- canonical-head mismatch;
- projection exceeding its declared hard budget without an explicit overflow policy;
- Markdown import with silently discarded blocks;
- projection claiming records not bound to its source head.

Readable output is not proof of a valid canonical state.

## 16. Security and privacy

The v0.1 public repository must be testable without real Residence data.

Required development policy:

- synthetic residents and memory fixtures only;
- no real private Residence roots in tests;
- no network requirement for core validation;
- no automatic background write service;
- no model/provider token or secret stored in fixtures;
- no write authority inferred from read access;
- no canonical mutation from a projection alone;
- external/imported content treated as data, not executable instructions.

## 17. Non-goals for v0.1

MNEME v0.1 does not attempt to provide:

- a production dynamic database;
- a vector database platform;
- autonomous identity creation;
- identity merging;
- cloud federation;
- cross-provider transport;
- general-purpose knowledge graph inference;
- unrestricted semantic deduplication;
- background autonomous memory rewriting;
- a full UI;
- replacement of MLF or MMLC;
- proof that matrix representation is always superior to text.

## 18. Initial implementation scope

After this design is approved, the first implementation plan should target a narrow **Fresh Memory Core**:

```text
1. package skeleton and schemas
2. canonical MemoryRecord parser/validator
3. append-only transaction staging/commit
4. exact-head and digest checks
5. deterministic JSONL store
6. route resolution for global + identity + project scopes
7. budgeted Markdown projection
8. truncation/corruption negative fixtures
9. Markdown import proposal + import-loss report
10. synthetic SOACR-facing read adapter contract
```

Deferred until later milestones:

```text
dynamic database backend
vector routing
advanced semantic compression
real Residence migration
live LIMEN authorization integration
full SOACR writeback
federation
UI / control plane
```

## 19. Acceptance criteria for the first implementation milestone

The implementation milestone is not complete unless all of the following are demonstrated with synthetic fixtures:

### A0 — Canonical determinism

The same ordered inputs produce byte-identical canonical record and receipt outputs.

### A1 — Truncation rejection

At least these injected failures must produce zero canonical commit:

- truncated JSON record;
- missing final transaction marker;
- wrong record count;
- wrong record digest;
- wrong expected head.

### A2 — Projection isolation

Two projections with different budgets may differ while binding to the same canonical head. Projection changes do not mutate canonical records.

### A3 — Budget enforcement

A generated model/Markdown projection must not exceed its declared hard budget. Overflow must be explicit and testable.

### A4 — Scope isolation

An identity-scoped route must not return records owned exclusively by another identity scope without explicit authorized cross-scope relation/policy.

### A5 — Import non-destruction

Markdown import must leave the original source untouched and produce an explicit import-loss report.

### A6 — Negative evidence

Each positive acceptance path must have at least one corrupted or unauthorized counterpart that turns the gate red.

## 20. Design closure

MNEME v0.1 establishes the following architectural commitment:

> Persistent memory is a canonical state of typed records and validated transactions. Markdown, model context, indexes, and graphs are projections of that state, not substitutes for it.

This allows memory capacity to grow independently of any single model context window or host bootstrap-file limit while preserving human-readable Markdown as a first-class, rebuildable interface.

The first implementation must stay file-first, deterministic, synthetic, auditable, and fail-closed. Dynamic database integration is intentionally postponed until the record/route/transaction contracts are stable.
